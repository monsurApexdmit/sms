# School Management – new system

FastAPI backend and React frontend that replace the CodeIgniter app in the parent folder.
Both run on the **existing `sms` database schema unchanged** (`../sqldatabase/sms.sql`) and the existing `../uploads` folder, so current data, photos and documents keep working, and the old app can run next to the new one during the switch.

```
update_system/
  backend/    FastAPI + SQLAlchemy 2 (Python 3.12)
  frontend/   React 19 + TypeScript + Vite + shadcn/ui (Radix + Tailwind CSS 4)
  docker-compose.yml
```

## Database

The `sms` database lives in the `central_mysql` container (MySQL 9.5, port 3306), imported from `sqldatabase/sms.sql`.
It has a dedicated user `sms` that can only access the `sms` database. Its password is in `backend/.env` (git-ignored).

## Run locally

Backend:

```bash
cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env        # then set DATABASE_URL and SECRET_KEY
.venv/bin/alembic upgrade head   # creates the tables this system adds (see "Database migrations")
.venv/bin/uvicorn app.main:app --reload --port 8000
```

API docs: http://localhost:8000/api/docs

Without `REDIS_URL`, rate limits are kept per process and emails/SMS are sent in-process after the response, without retries. Redis and the worker are optional locally; to run them the production way:

```bash
docker run -d --name sms-redis -p 127.0.0.1:6379:6379 redis:7.4-alpine
echo 'REDIS_URL=redis://127.0.0.1:6379/0' >> .env
.venv/bin/rq worker --with-scheduler -c app.rq_settings --url redis://127.0.0.1:6379/0 notifications
```

Daily fee jobs (late fines, then due reminders) run with `.venv/bin/python -m scripts.daily_jobs`, or from *Fee setup*.

Frontend:

```bash
cd frontend
npm install
npm run dev                  # http://localhost:5173, proxies /api to :8000
```

UI components live in `frontend/src/components/ui` (generated with the shadcn CLI, then owned by this repo; `Button` has an extra `loading` prop). Shared form pieces such as `Combobox`, `DatePicker`, `Field` and `confirmAction` are next to them in `src/components`. Theme colours are CSS variables in `src/index.css`.

## Database migrations

The legacy tables come from `sqldatabase/sms.sql` and are not changed. Tables this system adds are created by Alembic migrations in `backend/migrations/` (so far: `audit_log`). Revision `0001` is an empty baseline for the legacy schema, so `alembic upgrade head` works on an existing database without any stamping.

```bash
cd backend
.venv/bin/alembic upgrade head                                  # apply pending migrations
.venv/bin/alembic revision --autogenerate -m "add fee_plan"     # new migration from models.py
```

Review autogenerated migrations before committing them: the legacy tables are mapped loosely in `models.py` (for example `Text` for `varchar` columns), so remove any changes to legacy tables the migration did not mean to make. The Docker image runs `alembic upgrade head` before starting the API.

**After pulling this change, run `alembic upgrade head` before restarting the API.** Saving marks, attendance, invoices, payments, accounts or settings fails until the `audit_log` table exists.

## Audit log

Every insert, update and delete made through this API on marks, attendance, online exam results, invoices, payments, enrolments, exams, grades, the six account tables and settings is written to `audit_log` in the same transaction, with the signed-in user and the old and new values. Passwords and secret settings are recorded as changed without their values. Admins see it under **Settings → Audit log** (`GET /api/audit-log`). Changes made through the old CodeIgniter app are not recorded.

## Homework

Teachers set homework for a class (or one section) in a subject they teach, with an optional attachment, due date and maximum marks; admins can set it for any subject. Students hand in text and/or one file until the due date (later only when "accept late submissions" is on, and then flagged late), and may replace their answer until it is graded. Teachers see every student the homework was set for, with or without a submission, and grade with marks and feedback; the parent gets an email the first time a submission is graded. Parents see their children's homework and grades. Files go to `uploads/homework/` and `uploads/homework_submission/` and are served through signed links. Tables: `homework`, `homework_submission` (migration `0005`).

## Leave

Students apply for their own leave, parents for their children, and teachers, librarians and accountants for themselves (**Attendance → Leave**). Student leave is decided by an admin or any teacher with a subject in the student's current class; staff leave by an admin. Leave an admin records is approved at once. A request counts school days only (holidays and weekly days off are skipped), may span at most 60 days and may not overlap another pending or approved request for the same person; the applicant can cancel it while it is pending. Approved leave shows as "On leave" on the daily attendance sheet, and no absence SMS is sent for those students. The parent (or the member of staff) is emailed the decision, and texted when SMS is set up.

## Period attendance and check-in

- **Period attendance** (*Attendance → Period attendance*): teachers see the periods of the class routine for their subjects on the chosen day, everyone starts as present and they tap the exceptions (absent, late, excused). Students on approved leave start as excused. The *Section day* tab shows a section × period grid. Daily attendance stays the official record: **Fill daily attendance** sets a student present if they were present or late in at least one period, absent if absent in every marked period, and leaves students with no marked period alone. Days already marked are kept unless *Replace days already marked* is ticked. It sends no absence SMS.
- **Check-in kiosk** (*Attendance → Check-in kiosk*, admin and staff): a USB barcode/QR or RFID reader types the card code into the focused box; where the browser supports the BarcodeDetector API the camera can scan too. A student scan marks today's daily attendance present; staff scans record check-in (and a later scan the check-out) on staff attendance. Scans after *Late after* are logged as late (the legacy daily table has no "late", so for students it shows on the scan log; staff get `late`). Repeat scans within the configured minutes are ignored.
- **ID cards & devices** (admin): issue cards (an RFID UID or a generated code; one active card per person), create cards for a whole class (the student code is used when set, so cards already printed keep working), revoke cards, and see the scan log. Printed ID cards carry the active card code as a Code 128 barcode.
- **Terminals**: each device gets a key shown once. It sends `POST /api/attendance-devices/punch` with header `X-Device-Key` and `{"card_uid": "...", "timestamp": "..."}` or `{"punches": [...]}` (naive timestamps are school time, `SCHOOL_TIMEZONE`). Only a hash of the key is stored; disabling the device or rotating the key revokes it.

## Import and export

- **Excel export**: the Students, Teachers, Parents, Invoices, Income & expenses, Attendance report, Tabulation sheet and Audit log screens have an *Export to Excel* button (`GET /api/export/<name>.xlsx`). It downloads what the screen's filters select, with the same access rules; numbers and dates are real spreadsheet values. Exports stop at 50,000 rows.
- **Marks import**: on *Marks entry*, *Download template* gives a CSV of the section's students with their current marks (`student_id, roll, name, mark_obtained, comment`). Fill it in and use *Import CSV*. Every row is checked first (student in that section, whole-number mark within the same limits as the screen, no duplicates); if any row is wrong nothing is saved and the errors are listed. A blank mark clears it; without a `comment` column existing comments are kept.
- **Student import**: *Students → Bulk import* (unchanged).

## Fees

**Finance → Fee setup** (admin, accountant) holds fee heads (Tuition, Bus…), one or more fee plans per class and year with instalments (shares of the plan total that add up to 100%) and an optional late fine, and per-student discounts or scholarships (percent off each instalment, or an amount off the whole plan spread over its instalments).

- **Generate invoices** on an instalment creates an ordinary invoice for every student enrolled in that class and year, after discounts, so cash, Stripe and PayPal payments work as before. Running it again skips students already billed. Amounts are whole currency units (the legacy `invoice.amount` column is an integer).
- **Daily jobs** (`python -m scripts.daily_jobs`; the `scheduler` compose service runs it every 24 hours, admins can also run it from Fee setup) set late fines on unpaid instalment invoices past their due date plus grace days (flat once, or per day late, always recalculated from the base amount so re-running is harmless), then email parents and students and text parents about invoices due within 3 days or overdue, at most once per invoice per day. "Today" is taken in `SCHOOL_TIMEZONE`.
- **Receipts**: every payment has a printable receipt at `/app/receipts/<payment id>`, linked from Income & expenses and from an invoice's payment history. Students see their own, parents their children's.

## Report cards

**Exams → Exam timetable** holds each exam's papers per class (overlapping papers of a class are flagged) and prints admit cards. **Exams → Report cards** shows and prints report cards per exam or for the whole year ("Annual"); print them one at a time or a whole class/section at once with the browser's print → Save as PDF.

- Grades come from the grade table by raw mark. Any subject with grade point 0 makes the exam a **Fail** with GPA 0; while marks are missing it is **Incomplete**; otherwise GPA is the mean grade point. Full marks per subject come from `mark.mark_total`, or 100.
- Positions rank by total (annual: weighted percentage) over the whole class and within the section; ties share a position (1, 1, 3).
- The annual result weighs each exam by **Exam weights** (admin, on the Report cards page); weights should add up to 100%. CGPA is the weighted GPA; any failed exam makes the year a Fail. While any weighted exam is missing or Incomplete, the annual card has no percentage or position (missing marks are not counted as 0), and no CGPA unless an exam was failed.
- Attendance is days present over working days (calendar holidays and weekly days off excluded) in the term the exam's papers fall in, or else the school year's dates; without dates, from the first to the last recorded attendance day.
- Admins and the class's teachers (class teacher, section teacher, or a teacher of one of its subjects) write the remark.

## Parent-teacher meetings

Admins plan a meeting day (**Campus → Parent-teacher meetings**): date, time window, minutes per meeting, an optional class, and the teachers taking part (default: every teacher of the class). Slots are generated per teacher and the day is added to the academic calendar for parents. Parents book one slot per teacher per child, only with teachers of that child's class and at least 2 hours ahead, and can cancel until the meeting starts; parent and teacher get an email for each booking and cancellation. Teachers see their own slots, can block free ones, and record whether the meeting took place with a private note parents never see. The day, times and teachers can change only while nothing is booked. The database enforces one active booking per slot (`meeting_booking.active_slot_id` is unique), so two parents clicking at once cannot both get it.

## Staff HR and payroll

**HR → Staff attendance** (admin) records each teacher, librarian and accountant per day as present, late, half day, absent or on leave. **Salary structures** (admin) hold basic pay, allowances and deductions with an effective date. **Payroll** (admin and accountant) creates a draft run for a month, which can be recalculated until it is finalized. Finalized payslips become visible to staff under **My payslips** and can be printed or saved as PDF.

For each month, payroll uses the latest salary structure in effect. Working days exclude weekly days off and calendar holidays. Working days with no attendance recorded are paid. When **Deduct unpaid absences** is on (setting `payroll_deduct_absence`), pay drops by basic ÷ working days for each absent day, and by half that for a half day. Approved leave is paid. Marking a run as paid records one "Salary" expense per payslip in Income & expenses, and running it again records nothing new. The rules are in `backend/app/services/payroll.py`, together with `record_staff_leave` / `clear_staff_leave`, which mark approved staff leave on the attendance sheet.

## Transport

**Campus → Transport** manages routes, stops, vehicles, drivers and which student rides where. A route is still a row of the legacy `transport` table, and a student's route is still `student.transport_id`, so the old app and the Transport & dormitory screen keep showing it; the new `student_transport` table adds the stop and pick-up/drop-off choice (it is ignored when the route was since changed on the student form). Route capacity is the seats of the route's active vehicles; assigning more students than that is allowed with a warning. Vehicle insurance/fitness and driving licences expiring within 30 days are listed on the admin dashboard (`GET /api/transport/expiring`). Students and parents see their route, stop, times, vehicle and driver phone. Deleting a route on the old screen leaves its stops in `route_stop`; they are not shown anywhere.

## Student records and certificates

Each student has a health profile and a timeline of health, discipline, counselling, achievement and other records (Students → the heart icon; students and parents use **Health & certificates**). Who sees what is enforced by the API:

- Health profile: admins edit it; admins and teachers who teach a subject in the student's class read it; the student and their parent read it.
- Records: admins see all. Teachers add records for students they teach, see the non-confidential ones plus confidential ones they wrote, and edit or delete only their own. Parents see non-confidential discipline and achievement records; students see only their non-confidential achievements. Counselling records are always confidential.
- The audit log records changes to medical notes and to counselling/confidential record text without their values.

Admins issue transfer, bonafide and character certificates from editable templates (**People → Certificates**; "Add default templates" creates the three standard ones). Templates use placeholders such as `{student_name}`, `{class}` and `{serial}`; a placeholder with no value on file prints as `________`. Serial numbers run per kind and calendar year (`TC-2026-0001`, `BC-…`, `CC-…`, `CERT-…`). The issued text is stored, so editing a template later does not change issued certificates. Printing uses the browser's "Save as PDF". Students and parents can print their own certificates until an admin cancels one. Anyone can check a printed serial at `GET /api/public/certificates/verify?serial=TC-2026-0001`, which returns only whether it is valid, its kind, issue date and the student's initials (rate-limited).

## Admissions

**People → Admissions** (admin; accountants can view). Online applications are off until an admin switches them on there and picks the admission year. While they are on, the public **Admission** page shows an application form (up to 5 documents: PDF, image or Word) next to the printable paper form; it is rate-limited per IP and uses the website's reCAPTCHA when a secret key is set. Applicants get a reference code and can look up the status with it and the phone number they gave (status only, no personal data). Staff review applications, record a decision (accepted/rejected emails the guardian when an email was given) and **enrol** accepted applicants: this creates the student account, links an existing parent with the given email or creates one, and enrols the student in the chosen section with the next free roll number. Paper forms and walk-ins are entered as office applications; enquiries (leads) have follow-up dates and can be turned into applications. The only public endpoints are `GET /api/public/admissions/options`, `POST /api/public/admissions` and `POST /api/public/admissions/status`.

## Analytics

**Analytics** (next to Dashboard) has five tabs for the running year: *At risk*, *Fees*, *Attendance*, *Exams* and *Workload*. Admins see everything; accountants only *Fees*; teachers see the classes they teach and only their own workload. Students and parents have no access. Admins also get two dashboard tiles (students at high risk, fees collected this month). Everything is computed from existing data; there are no analytics tables.

- **At-risk score** (0–100; high at 50+, medium at 25+). The defaults can be changed per request with the query parameters in brackets:
  - attendance below 75% (`min_attendance`) over the last 30 days (`days`): 30 points, or 40 when 15 or more points below. Only days that were marked count, so a section whose attendance isn't taken is not flagged.
  - failing subjects (grade point 0) in the latest exam with marks: 20 + 5 per extra subject, at most 30
  - a fall of 10+ percentage points (`drop`) from the previous exam: 15
  - any overdue invoice: 10. Fee-plan invoices are due on their instalment's due date; other invoices 30 days (`invoice_due_days`) after they were created
  - less than 60% (`min_homework`) of homework already due handed in, with at least 3 due: 10
  - 10 or more days (`max_leave_days`) of approved leave this year: 5
- **Fees:** billed vs collected for each of the last 12 months, the year's collection rate, outstanding by class, overdue amounts by days late (1–30, 31–60, 61–90, 90+), collection per fee-plan instalment, and a paged list of defaulters.
- The at-risk and defaulters lists export to Excel.

## Notifications and the installable app

Absence alerts, leave decisions, graded homework, fee reminders, meeting bookings, admission decisions and notices sent with "send SMS" all go through `app/services/notifications.py`. Each one appears in the app (bell in the header, **Settings → Notifications**) and is also sent on the channels the person chose for that category under **My profile → Notifications**: email, SMS, web push, WhatsApp. Until someone changes them, the defaults match what was sent before (absence alerts and notices by SMS, homework grades and meeting bookings by email, leave and fee reminders by both). Each address or phone number gets one message per event, so a parent and child sharing a phone get one SMS.

- **Web push**: an admin creates the VAPID keys under **Notifications → Delivery channels → Create keys** (stored in the `settings` table; replacing them signs every device out of push). To make a pair by hand: `.venv/bin/python -c "from app.services.notifications import generate_vapid_keys as g; print(*g(), sep='\n')"` and store them as the `vapid_public_key` / `vapid_private_key` settings. Users then press **Enable push on this device** on My profile. Push needs HTTPS and the production build (the service worker isn't registered by `npm run dev`); on iPhone it works only after **Add to Home Screen** (iOS 16.4+).
- **WhatsApp**: Meta WhatsApp Cloud API. In Meta's WhatsApp Manager create a phone number and a permanent system-user token, then enter the phone number ID and token under **Delivery channels**. Meta only allows free-form text to people who messaged the school in the last 24 hours, so for alerts create and get approved a *Utility* template whose body has one variable (`{{1}}`) and enter its name (and language, default `en`); the notification text fills the variable. Numbers are taken from each account's phone field and must include the country code.
- **Installable app (PWA)**: `frontend/public/manifest.webmanifest`, icons in `frontend/public/icons`, service worker `frontend/public/sw.js`. The worker caches only the app shell and the hashed `/assets/` files; `/api/` responses are never cached. Bump `VERSION` in `sw.js` to drop old caches. nginx serves `sw.js` and the manifest uncached.

## Docker

```bash
cat > .env <<EOF
DATABASE_URL=mysql+pymysql://sms:<password>@host.docker.internal:3306/sms?charset=utf8mb4
SECRET_KEY=<64 random characters>
FRONTEND_URL=http://localhost:8080
EOF
docker compose up --build    # app on http://localhost:8080
```

Compose runs the API (which applies migrations on start), an RQ `worker` for emails/SMS, Redis, a `scheduler` for the daily fee jobs and a `backup` service (see "Backups"). The api, worker, redis and backup services have health checks (`docker compose ps` shows them); the API's is `GET /api/health/ready`, which answers 503 when the database or Redis does not respond within 3 seconds (`/api/health` only says the process is up). It sets `ENVIRONMENT=production`, in which the API and worker **refuse to start** unless `SECRET_KEY` is a random value of at least 32 characters, `COOKIE_SECURE=true` and `REDIS_URL` is set. Secure cookies work on `http://localhost`; anywhere else, put the site behind HTTPS. Failed notification jobs are retried after 1, 5 and 30 minutes and then kept for 7 days in RQ's failed-job registry (`rq info --url redis://redis:6379/0`).

`docker compose --profile localdb up` adds a throwaway MariaDB loaded from `sms.sql` (see the comment in the compose file).

## Backups

The `backup` service runs `scripts/backup.sh` every `BACKUP_INTERVAL_HOURS` (24) hours, two minutes after it starts. Each run writes a gzipped `mysqldump` (single transaction, with routines and triggers) of the database in `DATABASE_URL` to `backups/daily/sms-YYYY-MM-DD_HHMM.sql.gz`, and a tar of the uploads folder (`BACKUP_UPLOADS`: `weekly` by default, or `daily` / `off`). The Sunday run (`BACKUP_WEEKLY_DAY=7`) is also kept in `backups/weekly/`. Old files are removed beyond `BACKUP_KEEP_DAILY` (14) daily and `BACKUP_KEEP_WEEKLY` (8) weekly copies. Set `BACKUP_DIR` to put them elsewhere, preferably on another disk, and copy them off the server too. Files are readable by root only, because they contain personal data. The container reports unhealthy when no backup has succeeded for two intervals.

**Disk space:** about (14 + 8) × the compressed dump size (text compresses roughly 5–10×, so a few MB per copy for a typical school), plus up to 8 copies of the uploads folder (photos and documents barely compress; with `BACKUP_UPLOADS=daily`, up to 22 copies). Check `du -sh ../uploads` before choosing.

The client image is `mysql:8.4` (`BACKUP_IMAGE` to change it); it works with MySQL 8.4/9.x and MariaDB servers. The legacy tables are MyISAM, which `--single-transaction` does not freeze, so a dump taken while the old app writes can be slightly inconsistent between those tables.

```bash
docker compose run --rm backup once                       # back up now
docker compose run --rm backup restore /backups/daily/sms-2026-11-03_0200.sql.gz --yes
tar -xzf backups/weekly/uploads-2026-11-01_0200.tar.gz -C ..   # restore uploads (as root; replaces ../uploads files)
```

Restoring replaces the tables in the dump and leaves other tables alone; stop the api, worker and scheduler first (`docker compose stop api worker scheduler`), then run `alembic upgrade head` if the dump is older than the code. Without Docker, run the script directly: `DATABASE_URL=... BACKUP_ROOT=./backups UPLOADS_DIR=../uploads scripts/backup.sh once` (needs `mysqldump`, `gzip`, `tar`).

## Monitoring

- **Errors:** set `SENTRY_DSN` (Sentry, or a self-hosted compatible server) to report unhandled errors from the API, the worker and the daily jobs. Nothing is sent while it is empty. Events carry no personal data: request bodies, cookies, query strings, `Authorization`/`Cookie`/device-key headers and user details are removed before sending. `SENTRY_TRACES_SAMPLE_RATE` (0 by default) turns on performance tracing.
- **Logs:** `LOG_FORMAT=json` writes one JSON object per line (`time`, `level`, `logger`, `message`, `exception`) for log collectors; the default is plain text.
- **Health:** `GET /api/health` (process up) and `GET /api/health/ready` (database and Redis reachable) for load balancers and uptime checks.

## Upgrading an existing install

1. Back up: `docker compose run --rm backup once` (or `scripts/backup.sh once`).
2. Get the new code: `git pull`.
3. Apply database changes: Docker does this when the api starts; without Docker run `cd backend && .venv/bin/pip install -r requirements.txt && .venv/bin/alembic upgrade head`.
4. Restart: `docker compose up -d --build`, or restart uvicorn, the worker and the frontend (`npm install && npm run build`).

Migrations only create (and fill) new tables; they never change the legacy tables, so the old CodeIgniter app keeps working on the same database.

## Tests

```bash
cd backend && .venv/bin/python -m pytest
cd frontend && npm run typecheck && npm run build && npm test
```

The backend tests use SQLite and need no database server. They include a check that **every** non-public endpoint rejects anonymous requests. The frontend tests (Vitest and Testing Library, `src/**/*.test.ts(x)`) cover the shared hooks and components and which pages each role can open.

GitHub Actions (`.github/workflows/update-system.yml`) runs both, applies every migration to the legacy `sms.sql` schema on MariaDB 10.11, MySQL 8.4 and MySQL 9.5 with a backup/restore round trip, and builds the Docker images.

## What changed compared to the CodeIgniter app

| Area | Old | New |
|---|---|---|
| Access control | Login checked inside each method; about 60 methods had none | Role checked on every route when it is registered, plus record-level checks (a student sees only their own data, a parent only their children's) |
| Mobile API | `authenticate=false` skipped all checks | Removed; the same API serves web and mobile with JWT |
| Passwords | Unsalted sha1 | argon2. Old sha1 hashes still log in and are upgraded on first login |
| Password reset | Anyone could reset anyone's password by email | Emailed link, valid for 30 minutes, works once |
| Uploads | Original name, any extension, served from the web root | Allowed file types only, renamed, images re-encoded, served through signed time-limited links |
| Sessions | Cookies without httpOnly, no CSRF protection | Short-lived access token kept in memory + httpOnly SameSite=strict refresh cookie |
| Online exam marking | Compared in the browser-submitted format | Marked on the server; answers never sent to the browser; time window enforced |
| Payments | Marked paid from the browser redirect | Stripe Checkout (marked paid only by Stripe's signed webhook) and PayPal (order created and captured by the server, which checks invoice, amount and currency before recording the payment) |
| Contact form | No spam protection | Rate-limited per IP; reCAPTCHA checked on the server when a secret key is set |

### Running next to the old app

The old CodeIgniter 3.1.7 app gets no more security updates and has the problems listed above (about 60 methods without a login check, unsalted sha1 passwords, password reset by email alone). While both apps share the database, do not expose the old one to the internet. Restrict it to the school network or a VPN, for example in nginx:

```nginx
location / {
    allow 10.0.0.0/8;       # school network
    allow 192.168.0.0/16;
    deny all;
    # ... existing PHP config ...
}
```

Set a date to switch it off once staff have moved to the new app, then set `PASSWORD_HASH_SCHEME=argon2`.

### Settings to know

- `ENVIRONMENT`: `development` (default) or `production`; see the Docker section for what production requires.
- `REDIS_URL`: shared rate limits and the email/SMS job queue. Required in production.
- `SENTRY_DSN`, `SENTRY_TRACES_SAMPLE_RATE`, `LOG_FORMAT`: see "Monitoring".
- `BACKUP_DIR`, `BACKUP_INTERVAL_HOURS`, `BACKUP_KEEP_DAILY`, `BACKUP_KEEP_WEEKLY`, `BACKUP_UPLOADS`: see "Backups".

- `PASSWORD_HASH_SCHEME=sha1`: use this only while the old app still logs users in against the same database. With `argon2` (the default), users who log in through the new app can no longer log in through the old one.
- `SCHOOL_TIMEZONE`: the time zone online exam times are entered in.
- `STRIPE_WEBHOOK_SECRET`: required for online card payments. Point the Stripe webhook at `/api/payments/stripe/webhook`.
- PayPal: kept in the legacy `paypal` settings row, same format. Set `active`, `mode` (`sandbox` or `production`) and the REST app **client id and secret** for that mode (developer.paypal.com → Apps & Credentials); rows saved by the old app have no secret yet. Students and parents then see a PayPal button on unpaid invoices. The server creates the order for the amount still due in the `currency` setting, PayPal sends the user back to `/app/my-invoices`, and the server captures the order and records it once (the payment row's description holds `paypal:<capture id>`). The currency must be one PayPal supports. Payments PayPal holds for review stay unpaid and are recorded by staff.
- Contact form on the public website: messages are emailed to the website's contact email (website setting `email`), or `system_email` when that is empty; the form is hidden when neither is set. SMTP must be configured. For reCAPTCHA v2, set both the site key and the secret key (`recaptcha_secret_key`, stored in `frontend_general_settings` and never shown again after saving) in the website settings.
- SMS: `active_sms_service` may be `clickatell`, `twilio` or `msg91`. Clickatell uses the legacy HTTP API with `clickatell_user`, `clickatell_password` and `clickatell_api_id`. SMS is used for absence alerts, exam marks, and notices saved with "send SMS".

### Not ported
