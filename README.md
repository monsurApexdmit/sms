# School Management – new system

FastAPI backend and React frontend that replace the CodeIgniter app in the parent folder.
Both run on the **existing `sms` database schema unchanged** (`../sqldatabase/sms.sql`) and the existing `../uploads` folder, so current data, photos and documents keep working, and the old app can run next to the new one during the switch.

```
update_system/
  backend/    FastAPI + SQLAlchemy 2 (Python 3.12)
  frontend/   React 19 + TypeScript + Vite + shadcn/ui (Radix + Tailwind CSS 4)
  docker-compose.yml
```

## Database

The `sms` database lives in the `central_mysql` container (MySQL 9.5, port 3306), imported from `sqldatabase/sms.sql`.
It has a dedicated user `sms` that can only access the `sms` database. Its password is in `backend/.env` (git-ignored).

## Run locally

Backend:

```bash
cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env        # then set DATABASE_URL and SECRET_KEY
.venv/bin/alembic upgrade head   # creates the tables this system adds (see "Database migrations")
.venv/bin/uvicorn app.main:app --reload --port 8000
```

API docs: http://localhost:8000/api/docs

Without `REDIS_URL`, rate limits are kept per process and emails/SMS are sent in-process after the response, without retries. To run them the production way:

```bash
docker run -d --name sms-redis -p 127.0.0.1:6379:6379 redis:7.4-alpine
echo 'REDIS_URL=redis://127.0.0.1:6379/0' >> .env
.venv/bin/rq worker --with-scheduler --url redis://127.0.0.1:6379/0 notifications
```

Frontend:

```bash
cd frontend
npm install
npm run dev                  # http://localhost:5173, proxies /api to :8000
```

UI components live in `frontend/src/components/ui` (generated with the shadcn CLI, then owned by this repo; `Button` has an extra `loading` prop). Shared form pieces such as `Combobox`, `DatePicker`, `Field` and `confirmAction` are next to them in `src/components`. Theme colours are CSS variables in `src/index.css`.

### Accounts

Either set a password for it, or load demo data (one account per role, password `Demo@12345`):

```bash
cd backend && .venv/bin/python -m scripts.seed_demo --yes
```

## Database migrations

The legacy tables come from `sqldatabase/sms.sql` and are not changed. Tables this system adds are created by Alembic migrations in `backend/migrations/` (so far: `audit_log`). Revision `0001` is an empty baseline for the legacy schema, so `alembic upgrade head` works on an existing database without any stamping.

```bash
cd backend
.venv/bin/alembic upgrade head                                  # apply pending migrations
.venv/bin/alembic revision --autogenerate -m "add fee_plan"     # new migration from models.py
```

Review autogenerated migrations before committing them: the legacy tables are mapped loosely in `models.py` (for example `Text` for `varchar` columns), so remove any changes to legacy tables the migration did not mean to make. The Docker image runs `alembic upgrade head` before starting the API.

**After pulling this change, run `alembic upgrade head` before restarting the API.** Saving marks, attendance, invoices, payments, accounts or settings fails until the `audit_log` table exists.

## Audit log

Every insert, update and delete made through this API on marks, attendance, online exam results, invoices, payments, enrolments, exams, grades, the six account tables and settings is written to `audit_log` in the same transaction, with the signed-in user and the old and new values. Passwords and secret settings are recorded as changed without their values. Admins see it under **Settings → Audit log** (`GET /api/audit-log`). Changes made through the old CodeIgniter app are not recorded.

## Homework

Teachers set homework for a class (or one section) in a subject they teach, with an optional attachment, due date and maximum marks; admins can set it for any subject. Students hand in text and/or one file until the due date (later only when "accept late submissions" is on, and then flagged late), and may replace their answer until it is graded. Teachers see every student the homework was set for, with or without a submission, and grade with marks and feedback; the parent gets an email the first time a submission is graded. Parents see their children's homework and grades. Files go to `uploads/homework/` and `uploads/homework_submission/` and are served through signed links. Tables: `homework`, `homework_submission` (migration `0005`).

## Leave

Students apply for their own leave, parents for their children, and teachers, librarians and accountants for themselves (**Attendance → Leave**). Student leave is decided by an admin or any teacher with a subject in the student's current class; staff leave by an admin. Leave an admin records is approved at once. A request counts school days only (holidays and weekly days off are skipped), may span at most 60 days and may not overlap another pending or approved request for the same person; the applicant can cancel it while it is pending. Approved leave shows as "On leave" on the daily attendance sheet, and no absence SMS is sent for those students. The parent (or the member of staff) is emailed the decision, and texted when SMS is set up.

## Import and export

- **Excel export**: the Students, Teachers, Parents, Invoices, Income & expenses, Attendance report, Tabulation sheet and Audit log screens have an *Export to Excel* button (`GET /api/export/<name>.xlsx`). It downloads what the screen's filters select, with the same access rules; numbers and dates are real spreadsheet values. Exports stop at 50,000 rows.
- **Marks import**: on *Marks entry*, *Download template* gives a CSV of the section's students with their current marks (`student_id, roll, name, mark_obtained, comment`). Fill it in and use *Import CSV*. Every row is checked first (student in that section, whole-number mark within the same limits as the screen, no duplicates); if any row is wrong nothing is saved and the errors are listed. A blank mark clears it; without a `comment` column existing comments are kept.
- **Student import**: *Students → Bulk import* (unchanged).

## Fees

**Finance → Fee setup** (admin, accountant) holds fee heads (Tuition, Bus…), one or more fee plans per class and year with instalments (shares of the plan total that add up to 100%) and an optional late fine, and per-student discounts or scholarships (percent off each instalment, or an amount off the whole plan spread over its instalments).

- **Generate invoices** on an instalment creates an ordinary invoice for every student enrolled in that class and year, after discounts, so cash, Stripe and PayPal payments work as before. Running it again skips students already billed. Amounts are whole currency units (the legacy `invoice.amount` column is an integer).
- **Daily jobs** (`python -m scripts.daily_jobs`; the `scheduler` compose service runs it every 24 hours, admins can also run it from Fee setup) set late fines on unpaid instalment invoices past their due date plus grace days (flat once, or per day late, always recalculated from the base amount so re-running is harmless), then email parents and students and text parents about invoices due within 3 days or overdue, at most once per invoice per day. "Today" is taken in `SCHOOL_TIMEZONE`.
- **Receipts**: every payment has a printable receipt at `/app/receipts/<payment id>`, linked from Income & expenses and from an invoice's payment history. Students see their own, parents their children's.

## Report cards

**Exams → Exam timetable** holds each exam's papers per class (overlapping papers of a class are flagged) and prints admit cards. **Exams → Report cards** shows and prints report cards per exam or for the whole year ("Annual"); print them one at a time or a whole class/section at once with the browser's print → Save as PDF.

- Grades come from the grade table by raw mark. Any subject with grade point 0 makes the exam a **Fail** with GPA 0; while marks are missing it is **Incomplete**; otherwise GPA is the mean grade point. Full marks per subject come from `mark.mark_total`, or 100.
- Positions rank by total (annual: weighted percentage) over the whole class and within the section; ties share a position (1, 1, 3).
- The annual result weighs each exam by **Exam weights** (admin, on the Report cards page); weights should add up to 100%. CGPA is the weighted GPA; any failed exam makes the year a Fail.
- Attendance is days present over working days (calendar holidays and weekly days off excluded) in the term the exam's papers fall in, or else the school year's dates; without dates, from the first to the last recorded attendance day.
- Admins and the class's teachers (class teacher, section teacher, or a teacher of one of its subjects) write the remark.

## Parent-teacher meetings

Admins plan a meeting day (**Campus → Parent-teacher meetings**): date, time window, minutes per meeting, an optional class, and the teachers taking part (default: every teacher of the class). Slots are generated per teacher and the day is added to the academic calendar for parents. Parents book one slot per teacher per child, only with teachers of that child's class and at least 2 hours ahead, and can cancel until the meeting starts; parent and teacher get an email for each booking and cancellation. Teachers see their own slots, can block free ones, and record whether the meeting took place with a private note parents never see. The day, times and teachers can change only while nothing is booked. The database enforces one active booking per slot (`meeting_booking.active_slot_id` is unique), so two parents clicking at once cannot both get it.

## Staff HR and payroll

**HR → Staff attendance** (admin) records each teacher, librarian and accountant per day as present, late, half day, absent or on leave. **Salary structures** (admin) hold basic pay, allowances and deductions with an effective date. **Payroll** (admin and accountant) creates a draft run for a month, which can be recalculated until it is finalized. Finalized payslips become visible to staff under **My payslips** and can be printed or saved as PDF.

For each month, payroll uses the latest salary structure in effect. Working days exclude weekly days off and calendar holidays. Working days with no attendance recorded are paid. When **Deduct unpaid absences** is on (setting `payroll_deduct_absence`), pay drops by basic ÷ working days for each absent day, and by half that for a half day. Approved leave is paid. Marking a run as paid records one "Salary" expense per payslip in Income & expenses, and running it again records nothing new. The rules are in `backend/app/services/payroll.py`, together with `record_staff_leave` / `clear_staff_leave`, which mark approved staff leave on the attendance sheet.

## Docker

```bash
cat > .env <<EOF
DATABASE_URL=mysql+pymysql://sms:<password>@host.docker.internal:3306/sms?charset=utf8mb4
SECRET_KEY=<64 random characters>
FRONTEND_URL=http://localhost:8080
EOF
docker compose up --build    # app on http://localhost:8080
```

Compose runs the API (which applies migrations on start), an RQ `worker` for emails/SMS, and Redis. It sets `ENVIRONMENT=production`, in which the API and worker **refuse to start** unless `SECRET_KEY` is a random value of at least 32 characters, `COOKIE_SECURE=true` and `REDIS_URL` is set. Secure cookies work on `http://localhost`; anywhere else, put the site behind HTTPS. Failed notification jobs are retried after 1, 5 and 30 minutes and then kept for 7 days in RQ's failed-job registry (`rq info --url redis://redis:6379/0`).

`docker compose --profile localdb up` adds a throwaway MariaDB loaded from `sms.sql` (see the comment in the compose file).

## What changed compared to the CodeIgniter app

| Area | Old | New |
|---|---|---|
| Access control | Login checked inside each method; about 60 methods had none | Role checked on every route when it is registered, plus record-level checks (a student sees only their own data, a parent only their children's) |
| Mobile API | `authenticate=false` skipped all checks | Removed; the same API serves web and mobile with JWT |
| Passwords | Unsalted sha1 | argon2. Old sha1 hashes still log in and are upgraded on first login |
| Password reset | Anyone could reset anyone's password by email | Emailed link, valid for 30 minutes, works once |
| Uploads | Original name, any extension, served from the web root | Allowed file types only, renamed, images re-encoded, served through signed time-limited links |
| Sessions | Cookies without httpOnly, no CSRF protection | Short-lived access token kept in memory + httpOnly SameSite=strict refresh cookie |
| Online exam marking | Compared in the browser-submitted format | Marked on the server; answers never sent to the browser; time window enforced |
| Payments | Marked paid from the browser redirect | Stripe Checkout (marked paid only by Stripe's signed webhook) and PayPal (order created and captured by the server, which checks invoice, amount and currency before recording the payment) |
| Contact form | No spam protection | Rate-limited per IP; reCAPTCHA checked on the server when a secret key is set |

### Running next to the old app

The old CodeIgniter 3.1.7 app gets no more security updates and has the problems listed above (about 60 methods without a login check, unsalted sha1 passwords, password reset by email alone). While both apps share the database, do not expose the old one to the internet. Restrict it to the school network or a VPN, for example in nginx:

```nginx
location / {
    allow 10.0.0.0/8;       # school network
    allow 192.168.0.0/16;
    deny all;
    # ... existing PHP config ...
}
```

Set a date to switch it off once staff have moved to the new app, then set `PASSWORD_HASH_SCHEME=argon2`.

### Settings to know

- `ENVIRONMENT`: `development` (default) or `production`; see the Docker section for what production requires.
- `REDIS_URL`: shared rate limits and the email/SMS job queue. Required in production.

- `PASSWORD_HASH_SCHEME=sha1`: use this only while the old app still logs users in against the same database. With `argon2` (the default), users who log in through the new app can no longer log in through the old one.
- `SCHOOL_TIMEZONE`: the time zone online exam times are entered in.
- `STRIPE_WEBHOOK_SECRET`: required for online card payments. Point the Stripe webhook at `/api/payments/stripe/webhook`.
- PayPal: kept in the legacy `paypal` settings row, same format. Set `active`, `mode` (`sandbox` or `production`) and the REST app **client id and secret** for that mode (developer.paypal.com → Apps & Credentials); rows saved by the old app have no secret yet. Students and parents then see a PayPal button on unpaid invoices. The server creates the order for the amount still due in the `currency` setting, PayPal sends the user back to `/app/my-invoices`, and the server captures the order and records it once (the payment row's description holds `paypal:<capture id>`). The currency must be one PayPal supports. Payments PayPal holds for review stay unpaid and are recorded by staff.
- Contact form on the public website: messages are emailed to the website's contact email (website setting `email`), or `system_email` when that is empty; the form is hidden when neither is set. SMTP must be configured. For reCAPTCHA v2, set both the site key and the secret key (`recaptcha_secret_key`, stored in `frontend_general_settings` and never shown again after saving) in the website settings.
- SMS: `active_sms_service` may be `clickatell`, `twilio` or `msg91`. Clickatell uses the legacy HTTP API with `clickatell_user`, `clickatell_password` and `clickatell_api_id`. SMS is used for absence alerts, exam marks, and notices saved with "send SMS".

### Not ported

- PayUMoney: the service was shut down and merged into PayU, so the old integration (which also confirmed payments in the browser) has nothing to talk to. Stripe and PayPal are implemented.
- In-browser database backup/restore, the updater, and the installer. Use database-level backups and Docker images instead.
- The admin screen for editing translation phrases. The interface is English only.
- Barcode and ID-card printing.
